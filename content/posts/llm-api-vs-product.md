요즘 주변에서 "우리 서비스에도 AI 에이전트 하나 붙이자"는 얘기가 진짜 쉽게 나온다. 데모만 보면 프롬프트 몇 줄에 툴 몇 개 연결하면 금방 끝날 것 같으니까. 나도 처음엔 모델 성능이 이만큼 올라왔으니 아키텍처 설계가 예전보다 단순해지겠거니 싶었다.

막상 현업에서 아키텍처를 잡아보면 정반대다. 오히려 전통적인 백엔드 설계할 때보다 신경 쓸 게 더 늘어났다.

가장 먼저 부딪히는 건 '비결정성'이다. 일반 API는 같은 입력을 넣으면 같은 응답이 오고, 에러가 나면 예외 코드로 떨어진다. 근데 LLM이 낀 흐름은 멀쩡히 돌다가도 가끔 엉뚱한 JSON을 뱉거나, 툴 호출 순서를 자기 마음대로 바꾼다. 결국 모델 앞단보다 **뒷단 가드레일과 상태 복구 로직**에 코드가 훨씬 많이 들어간다.

두 번째는 지연 시간(Latency)과 비용 구조다. 데모에선 응답 5초 걸려도 "오 신기하다" 하고 넘어가지만, 실제 사용자가 쓰는 서비스에선 3초만 넘어가도 이탈한다. 그래서 요즘 아키텍트 입장에서 제일 많이 고민하는 건 "무슨 모델을 쓸까"보다 이렇다.

- 굳이 비싼 추론 모델까지 안 가도 되는 단순 분기는 어디서 자를지
- 컨텍스트를 매번 다 밀어 넣지 않고 어떻게 캐싱하고 요약해서 넘길지
- 에이전트가 중간에 뻗었을 때 사용자한테 어디까지 롤백해서 보여줄지

결국 AI 시대라고 해서 소프트웨어 공학의 기본이 사라지는 게 아니더라. 오히려 "확률적으로 움직이는 컴포넌트 하나를, 어떻게 결정론적인 시스템 안에 안전하게 가둬서 굴릴 것인가"라는 꽤 고전적인 시스템 설계 문제로 돌아온 느낌이다.

요즘은 프롬프트 잘 깎는 것도 중요하지만, 모델이 헛발질해도 시스템 전체가 안 무너지게 경계를 그어 주는 설계가 훨씬 값어치가 커지고 있다. 나도 당분간은 새 모델 따라가는 것만큼이나 이 '경계 긋기' 패턴들을 하나씩 정리해 보려고 한다.
